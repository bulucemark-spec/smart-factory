1. 需求评审结论

1.1 总体评价

V2.0 文档业务覆盖完整、技术选型主流、非功能指标明确，已具备进入开发的条件。但作为评审稿，它描述的是"目标态全景"，缺少从 0 到 1 的落地路径、领域契约与一致性设计。若直接按功能清单平行开工，极易出现：服务边界混乱、跨服务联调困难、AI 场景等不到数据、试点期运维成本过高。

1.3 范围裁剪原则（本次垂直切片）

  • 做透一条链：登录/权限 → 主数据 → 到货收货 → IQC → 上架 → 工单/领料 → 开工报工 → 完工入库 → OQC → 销售出库，外加 NCR→MRB→CAPA 不合格闭环与 RAG 助手/根因分析。
  • 做浅但留口：APS（先规则排产，遗传/强化学习留口）、SPC（先数据采集+控制图/Cpk 计算，八大判异留口）、OEE（先可用率/性能/质量计算）、盘点/Andon（建表与基础接口）。
  • 暂不做：PLC 控制、TMS、LIMS、大模型训练、完整 K8s 双活（明确为后续迭代）。

2.2 为什么试点期"做减法"是专业选择

  • Nacos/注册发现：Compose 内服务名固定、网络稳定，用配置化 URL + Feign 直连即可；引入 Nacos 增加约 1GB 内存与启动顺序依赖，试点期收益为零。
  • RocketMQ/Seata：核心链路用"本地事务 + Feign 编排 + 状态机 + 幂等 + 补偿"即可正确演示；MQ 事务消息与 Saga 是高并发/多编排方下的生产增强，二期按需引入。
  • Milvus/ClickHouse：RAG 在文档量级 < 10 万切片时，TF-IDF/向量内存检索足够；报表在试点数据量下 MySQL 聚合即可。避免"用大炮打蚊子"。
  • 所有被裁剪组件均在代码中预留扩展点（接口抽象、配置开关），二期替换不改业务代码。

2.3 二期目标态（与文档一致）

模块化/轻量服务 → 完整 Spring Cloud（Nacos+Sentinel+Seata+Gateway）+ RocketMQ 事件驱动 + Milvus/ClickHouse/TimescaleDB + EMQX/OPC UA IoT 接入 + K8s/Helm/ArgoCD + GPU 推理。

边界纪律：

  1. 每个服务只读写自己的库，禁止跨库 JOIN；关联数据通过 Feign 获取或冗余快照（带 _name 冗余字段，主数据变更走事件/对账）。
  2. 服务间只传递 ID 与必要快照，不暴露内部实体。
  3. 对外统一走 gateway 的 /api/<strong>，服务间走 /internal/</strong>（仅容器网络可达，不被 gateway 暴露）。

4. 领域模型（核心聚合）

完整字段以 db/init/*.sql 为准，此处描述聚合与关系。

4.1 system（基础平台 + 主数据）

  • 组织聚合：Org（集团-工厂-车间-产线-班组，自关联 parent_id，物化路径 path）。
  • 身份聚合：User ↔ UserRole ↔ Role ↔ RolePermission ↔ Permission（RBAC + 数据权限维度 org_id）。
  • 物料聚合：Material（编码、分类、单位、批次/效期开关、ABC、重量）。
  • 供应商聚合：Supplier（资质、等级 grade、合格率、PPM）。
  • BOM 聚合：Bom（产品 + 版本 + 状态） 1—n BomItem（子物料、用量、序号）。
  • 工艺聚合：WorkCenter（工作中心/产能）；Routing（产品+版本）1—n RoutingOperation（工序序号、工作中心、标准工时、是否质检点 CTQ）。

4.2 wms（仓储）

  • 仓库聚合：Warehouse 1—n Zone 1—n Location（坐标 x/y、容量、类型、状态）。
  • 收货聚合：Asn 1—n AsnItem；Receipt 1—n ReceiptItem（实收批次、数量）。
  • 库存聚合：Inventory（库位+物料+批次+状态 唯一）；批次状态机见 §5.4。
  • 任务聚合：PutawayTask（上架）；PickWave 1—n PickTask（拣货，关联工单/出库单）。
  • 出库聚合：Outbound 1—n OutboundItem（销售出库/领料）。

4.3 mes（制造执行）

  • 工厂聚合：Workstation（工位，绑定工作中心/产线）。
  • 工单聚合：WorkOrder（产品、BOM、工艺路线、计划/完工/不良数量、状态、计划起止）。
  • 报工聚合：WorkReport（工单、工序、工位、操作员、合格/不良/报废、不良代码）。
  • 投料聚合：MaterialTxn（工单、物料、批次、数量、领/退）。
  • 谱系聚合：Genealogy（成品批次 parent_batch ↔ 物料批次 child_batch、工单、数量）。

4.4 qms（质量）

  • 标准聚合：InspectionStandard（物料+供应商+类型+AQL 水平）1—n InspectionItem（项目、上下限、量具、CTQ）。
  • 检验聚合：InspectionTask（类型、来源单号、物料/批次、样本数、状态）1—n InspectionResult（项目、实测值、判定）。
  • 不合格聚合：Ncr（来源、批次、数量、缺陷、等级、处置方式、状态）1—1/1—n Capa（根因、纠正措施、责任人、期限、验证）。
  • SPC 聚合：SpcRecord（特性、值、时间）→ 控制图统计量 / Cpk。

5. 核心状态机（显式校验，禁止非法跳变）

5.1 工单 WorkOrder

CREATED 已创建
  └─release()► RELEASED 已下发 ──pick()► PICKED 已拣料
                   │                    └─start()► STARTED 开工
                   │                                 └─report()► RUNNING 报工中
                   │                                                └─complete()► COMPLETED 完工
                   │                                                                 └─stockIn()► STOCKED 已入库 ─close()► CLOSED 已关闭
                   └──────────────────────────────────────（任意未完工）cancel()► CANCELLED

返工/试产/外协为 type 维度，复用同一状态机。

5.2 检验任务 InspectionTask

PENDING 待检 ─submit(结果)► JUDGING 判定中
   ├─全部合格► QUALIFIED 合格
   └─存在不合格► UNQUALIFIED 不合格 ──（NCR/MRB 处置后）► DISPOSED 已处置

判定规则：任一 CTQ 项实测值超出 [LSL, USL] 即不合格；非 CTQ 按 AQL 不合格数阈值。

5.3 NCR

OPEN 待MRB ─MRB评审► REVIEWED 已评审(处置方式) ─执行► IN_PROGRESS 处置中
   └─CAPA完成且验证有效► CLOSED 已关闭；VERIFY_FAIL 验证不通过 → 回 IN_PROGRESS

处置方式 disposition ∈ {RETURN 退货, SORT 挑选, REWORK 返工, CONCESSION 让步, SCRAP 报废}。

5.4 库存批次状态 Inventory.status

PENDING 待检 ─IQC合格+上架► QUALIFIED 合格 ──拣货/出库►（数量扣减）
PENDING       ─IQC不合格► FROZEN 冻结 ─MRB► {退货出库/报废 SCRAPPED/解冻回 QUALIFIED(让步)}
QUALIFIED     ─质量异常► FROZEN

FIFO：合格库存按 expiry_date ASC, production_date ASC, id ASC 推荐出库批次。

6. 核心闭环时序（Feign 编排链）

约定：→ 为同步 Feign/HTTP；每个跨服务写操作都要求幂等键与状态前置校验。
  1. 收货 → IQC

WMS 收货登记（写 Receipt + 待检 Inventory，本地事务） → QMS /internal/iqc/tasks（按物料+供应商匹配检验方案，建 IQC 任务，PENDING）。

  1. IQC 判定 → 上架/冻结

QMS 录入结果并判定 → 合格：WMS /internal/inventory/qualified（生成 PutawayTask，库存待上架） → 不合格：WMS /internal/inventory/freeze（冻结批次）+ QMS 建 NCR。

  1. 上架：WMS 执行 PutawayTask，库存迁至正式库位、状态 QUALIFIED。
  2. 工单下发 → 领料

MES release（CREATED→RELEASED，按 BOM 展开） → WMS /internal/pick-waves（按工单 BOM 生成领料波次/拣货任务，FIFO 预占批次）。

  1. 拣货 → 线边交接

WMS 执行拣货（扣减/预占合格库存）；MES /work-orders/{id}/receive-materials → 拉取 WMS 拣货结果，写 MaterialTxn + Genealogy(child 批次)，工单 PICKED→STARTED。

  1. 开工报工：MES 写 WorkReport，累加工单合格/不良/报废；不良可触发 QMS IPQC/NCR。
  2. 完工 → 成品入库 + OQC

MES complete（→STOCKED 前）→ WMS /internal/finished-goods/inbound（成品仓入库，成品批次，写 Genealogy parent） → QMS /internal/oqc/tasks（OQC 检验）。

  1. OQC 判定：合格 → WMS 成品批次放行 QUALIFIED；不合格 → 冻结 + NCR。
  2. 销售出库：WMS 建 Outbound（FIFO 推荐批次）→ 拣货复核 → 扣减库存 → 发运签收。
  3. 不合格闭环：NCR → MRB（处置方式）→ 联动 WMS（退货出库/报废/解冻）→ CAPA（措施/责任人/期限）→ 验证 → 关闭、沉淀知识库。

7. API 契约规范

7.1 统一响应

{ "code": 0, "message": "success", "data": { }, "traceId": "..." }
  • 分页：data = { "records": [], "total": 0, "page": 1, "size": 20 }
  • code=0 成功；非 0 见错误码表。HTTP 状态：200 承载业务结果，4xx/5xx 表达协议/系统错误。

7.2 错误码（分段）

段含义
0成功
1000-1999通用（参数/认证/权限/资源不存在/冲突/系统）
2000-2999system / 主数据
3000-3999wms
4000-4999mes
5000-5999qms
6000-6999ai

典型：1001 未认证、1003 无权限、1004 参数错误、1005 资源不存在、1009 状态非法/冲突、3011 库存不足、3012 批次冻结、4011 工单状态非法、5011 检验项超限。

7.3 鉴权

  • 登录：POST /api/auth/login（username/password）→ accessToken（JWT）。
  • 后续请求头：Authorization: Bearer <token>。
  • gateway 校验 JWT，透传 X-User-Id / X-User-Name / X-User-Org / X-User-Roles；下游通过 UserContext 读取。
  • 放行清单：/api/auth/login、/actuator/health、静态资源。

7.4 命名与方法

  • RESTful 资源复数；查询用 GET + query；创建 POST；更新 PUT；状态动作用 POST /resource/{id}/{action}（如 /work-orders/12/release）。
  • 时间统一 ISO-8601；金额/数量用明确单位与精度；所有列表支持 page/size/keyword/排序。

8. 数据一致性、幂等与事务

  • 本地事务：单服务内多表写用 @Transactional，保证服务内强一致（如收货写 Receipt+Inventory）。
  • 跨服务最终一致：Feign 编排 + 状态机；每步先校验前置状态，失败抛业务错误并返回可读原因；关键写接口支持幂等键（requestId/业务单号唯一，重复请求返回首次结果）。
  • 防超扣/超发：库存扣减用条件更新 UPDATE ... SET qty=qty-? WHERE id=? AND qty>=?，影响行数=0 即库存不足（3011）。
  • 冻结优先：质量异常先冻结（FROZEN）再走流程，冻结批次不参与 FIFO 与可用量计算。
  • 冗余快照对账：跨域展示字段（物料名、供应商名）以冗余 _name 保存；二期由主数据变更事件刷新 + 定时对账。
  • 二期升级：引入 RocketMQ 事务消息（报工/扣库存原子性）+ Seata AT/Saga（长流程）+ 本地消息表（可靠投递）+ 死信与人工补偿台。

9. AI 服务设计

9.1 场景优先级矩阵（数据就绪度 × ROI × 难度）

场景业务 ROI数据就绪度落地难度建议批次
RAG 知识助手高（减少问询/培训成本）高（SOP/手册已存在）低本次（Iteration 0）
质量根因分析高（缩短排查）中（需结构化关联）中本次（LLM+检索先行）
OCR 仪表读数中高低Iteration 1
需求/库存预测高中（需历史销量）中Iteration 1-2
AI 视觉缺陷检测很高低（需大量标注）高Iteration 2（先标注体系/小样本）
预测性维护高低（需传感器历史）高Iteration 2-3（IoT 先行）
智能排产(RL/GA)中中高Iteration 3（规则 APS 稳定后）
关键洞察：视觉检测与预测性维护不是算法问题，是数据问题。必须先建标注/采集体系与 IoT 历史积累，否则模型无米下炊。本次先交付不依赖训练数据、ROI 明确的 RAG 与根因分析。

9.2 大模型接入（OpenAI 兼容，云端优先）

  • ai-service 通过环境变量配置，适配 DeepSeek / 通义千问 / 智谱 GLM / Kimi / 本地 vLLM·Ollama（OpenAI 兼容口） 等：
  • LLM_BASE_URL（如 https://api.deepseek.com）
  • LLM_API_KEY（你的密钥）
  • LLM_MODEL（如 deepseek-chat）
  • 仅调用标准 POST {BASE_URL}/v1/chat/completions（代码内自动兼容已含 /v1 与不含 /v1 的 base_url）。
  • 未配置 key 时自动降级 Mock：返回检索到的片段拼接与"当前为离线演示应答"，保证系统可完整离线演示与联调。
  • 安全：工艺机密默认走内网/本地模型或企业合规网关；云端仅发送检索片段与问题，不回传全量数据库。

9.3 RAG 设计（防幻觉、可溯源）

  • 知识源：SOP、设备手册、工艺文件、质量案例、客诉 8D（放 ai-service/knowledge/，启动时切片）。
  • 切片：按标题/段落分块（含 overlap），保留 来源文档 + 章节 元数据。
  • 检索：本次用 TF-IDF + 余弦相似度（零模型下载、稳定可离线）；二期替换为 bge-m3 向量 + Milvus（接口已抽象 Retriever）。
  • 生成：系统提示词强制"只依据给定片段回答，逐条标注 [来源]，片段不足或无关时明确说不知道并转人工"。
  • 回流：记录提问、检索命中、回答、点赞/点踩（bad case），供知识库与模型迭代（AI 可观测）。

9.4 根因分析

输入：现象（如 SPC 报警、不良率突增）+ 可选上下文（时段/设备/批次/人员）。检索历史案例与工艺知识，LLM 按 5M1E（人/机/料/法/环/测）鱼骨结构输出"可能原因排序 + 建议验证方法 + 参考案例"，同样强制引用、保留人工确认。

10. 安全设计（对标等保三级，试点期落地核心项）

  • 身份：JWT（短期 accessToken + 密钥轮换预留），BCrypt 存储密码（强度 10）。
  • 授权：RBAC + 数据权限（按工厂/车间/仓库 org 维度过滤），按钮/字段权限预留。
  • 传输：容器内/对外 TLS（试点 HTTP，生产由 Ingress/网关终结 TLS1.2+）。
  • 审计：关键增删改留痕（操作人、时间、模块、前后值摘要），日志留存策略二期对接 ELK。
  • 隔离：业务服务 /internal/** 不对外暴露；MinIO/MySQL/Redis 不直接映射公网端口（仅本地调试映射）。
  • 密钥：所有口令/密钥走环境变量/.env，不入库不入 Git（提供 .env.example）。
